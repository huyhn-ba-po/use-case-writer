# Examples — 2 Complete Use Cases

Use these as reference when writing UCs. Both examples have passed the full 20-point checklist. They use neutral, non-banking domains (e-commerce and facility booking) to illustrate the method, not any specific product.

---

## Example 1: UC-ORDER-01 — Place an order for a physical product

| **Use Case ID:** | UC-ORDER-01 |
| ---: | :--- |
| **Use Case Name:** | Place an order for a physical product |
| **Created By:** | \<TBD\> | **Last Updated By:** | \<TBD\> |
| **Date Created:** | YYYY-MM-DD | **Date Last Updated:** | YYYY-MM-DD |

| **Actor:** | **Primary:** Customer (registered account, email verified). **Secondary:** Payment Gateway, Inventory Service, Notification Service. |
| ---: | :--- |
| **Description:** | When a customer finds a product in the online store and decides to buy it, the customer reviews the order and completes checkout via the store platform. The UC ends when the payment is confirmed, the order is created with stock reserved, and a confirmation notification is sent. |
| **Preconditions:** | 1. Customer has logged in with a verified email address.<br>2. The selected product status is 'Published' and has available stock.<br>3. Customer's cart contains at least one item.<br>4. Payment Gateway is available and responsive. |
| **Postconditions:** | 1. Order record is created in the Orders table with status='Confirmed' and the order timestamp.<br>2. Stock for each ordered item is reserved (decremented) in the Inventory Service.<br>3. Payment transaction is recorded with status='Completed' and a unique transaction reference.<br>4. Confirmation email + in-app notification is sent to the customer within 60 seconds.<br>5. The cart is cleared. |
| **Priority:** | High — Core revenue-generating feature; blocks store MVP go-live. |
| **Frequency of Use:** | Estimated ~500 orders/day store-wide; peak ~100/hour during promotional campaigns and flash sales. |
| **Normal Course of Events:** | 1. Customer browses the catalog and clicks on a product card.<br>2. System displays the **Product Detail** page: description, price, availability, and an **Add to Cart** button.<br>3. Customer clicks **Add to Cart**, then **Checkout**.<br>4. System displays the **Order Summary** screen: items, original price, applicable discount (if any), and total amount due.<br>5. Customer selects a payment method (wallet, card, or gift card) and clicks **Proceed to Payment**.<br>6. System invokes UC-PAY-01 to process the payment.<br>7. Upon successful payment, system creates the order record and reserves stock in the Inventory Service.<br>8. System displays the **Order Confirmed** screen with an **Order Number** and a download link for the receipt.<br>9. System invokes UC-NOTI-01 to send the confirmation email and push notification to the customer. |
| **Alternative Courses:** | **UC-ORDER-01.AC.1: Pay using a gift card code**<br>At step 5 of the Normal Course, if the customer selects **Gift Card** as the payment method:<br>5a. System displays a gift card code input field.<br>5b. Customer enters the code and clicks **Apply**.<br>5c. System validates the gift card against the Gift_Cards table: checks expiry date, applicability, and remaining balance.<br>5d. System updates the total amount to 0 and displays "Gift card applied — fully covered".<br>5e. Customer clicks **Confirm Order** → continue from step 7 of the Normal Course (no payment gateway call needed).<br><br>**UC-ORDER-01.AC.2: Re-order from a past order**<br>At step 3 of the Normal Course, if the customer chooses **Buy Again** from their order history:<br>3a. System pre-fills the cart with the items from the selected past order.<br>3b. System re-checks current price and availability for each item.<br>3c. Customer reviews the cart → continue from step 4 of the Normal Course. |
| **Exceptions:** | **UC-ORDER-01.EX.1: Payment fails at gateway**<br>Trigger: At step 6, UC-PAY-01 returns a payment failure (insufficient funds, card declined, gateway timeout).<br>Response: System displays "Payment unsuccessful. Please check your payment details and try again." with a **Try Again** button and a **Choose Different Method** link.<br>Final state: No order record is created. The cart remains unchanged. The failed payment attempt is logged in Payment_Logs with the reason code from the gateway.<br><br>**UC-ORDER-01.EX.2: Item sells out between page load and checkout**<br>Trigger: At step 7, the Inventory Service returns an OUT_OF_STOCK error because another customer bought the last unit milliseconds earlier.<br>Response: System displays "Sorry, this item just sold out. Add it to your wishlist to be notified when it is back."<br>Final state: Payment is refunded automatically within 1 business day. No order record is created. Customer is offered the option to join the back-in-stock waitlist.<br><br>**UC-ORDER-01.EX.3: Gift card invalid or expired**<br>Trigger: At step 5c (AC.1), the gift card code does not exist, has expired, or has a zero balance.<br>Response: System displays an inline error: "Gift card is invalid or has expired. Please check the code or use another payment method."<br>Final state: No order is created. Customer can retry with a different code or choose another payment method.<br><br>**UC-ORDER-01.EX.4: Inventory Service unavailable during order creation**<br>Trigger: At step 7, the Inventory Service does not respond within 10 seconds when the system attempts to reserve stock.<br>Response: System displays "Your payment was successful. We are finalizing your order — this may take a few minutes. Check your email for confirmation."<br>Final state: Payment is recorded as 'Completed'. A background retry job attempts to reserve stock and create the order every 2 minutes for up to 30 minutes. Customer receives an email once the order is confirmed. If the retry fails after 30 minutes, the support team is alerted via an automated ticket. |
| **Includes:** | UC-PAY-01: Process payment (invoked at step 6 of the Normal Course)<br>UC-NOTI-01: Send order notification (invoked at step 9 of the Normal Course) |
| **Special Requirements:** | **Performance**: Product Detail page loads ≤ 2s; Order Summary and Order Confirmed screens load ≤ 1s. System supports 500 concurrent checkouts without degradation.<br>**Security**: Payment card data must never be stored on store servers; all card processing is delegated to a PCI-DSS certified Payment Gateway. Gift card balances must be validated server-side only — never expose remaining balance to the client.<br>**Reliability**: If the Inventory Service is unavailable at step 7, payment must NOT be rolled back — order creation must be retried asynchronously. No customer should pay and receive no order without a support escalation path.<br>**Usability**: The checkout flow must be completable in ≤ 3 taps on mobile (after payment-method selection).<br>**Compliance**: Issue a tax invoice for all transactions above the local statutory threshold, per applicable tax regulations. |
| **Assumptions:** | 1. Payment Gateway SLA is ≥ 99.5% uptime during business hours.<br>2. Gift cards are pre-loaded into the system before being distributed.<br>3. Customer's email is verified — confirmation emails will not bounce.<br>4. Stock reservation is synchronous under normal conditions (< 3s). |
| **Notes and Issues:** | [TBD-1] Should customers be able to gift an order to another account? \| Owner: Product Team \| Due: YYYY-MM-DD \| Resolution: TBD — deferred to phase 2.<br>[TBD-2] What is the refund policy if a customer requests a refund within 7 days of delivery? \| Owner: \<TBD\> \| Due: YYYY-MM-DD \| Resolution: TBD.<br>[NOTE] Coordinate with the Marketing team on the confirmation email template — must align with current brand guidelines. |

## Example 2: UC-ROOM-03 — Approve a meeting-room booking request

| **Use Case ID:** | UC-ROOM-03 |
| ---: | :--- |
| **Use Case Name:** | Approve a meeting-room booking request |
| **Created By:** | \<TBD\> | **Last Updated By:** | \<TBD\> |
| **Date Created:** | YYYY-MM-DD | **Date Last Updated:** | YYYY-MM-DD |

| **Actor:** | **Primary:** Facility Manager (active manager account). **Secondary:** Notification Service, Calendar Integration Service. |
| ---: | :--- |
| **Description:** | When a member submits a meeting-room booking request through the workspace platform, the request enters the facility manager's queue. The manager opens the management portal, reviews the request, and makes a decision: Approve, Decline, or Propose an Alternative Slot. The UC ends when the request has a final status and the member is notified of the outcome. |
| **Preconditions:** | 1. Facility Manager has logged in to the management portal with an active account.<br>2. At least one booking request is in the queue with status='Pending_Manager_Review'.<br>3. The requested time slot is within the room's published availability window.<br>4. The member still has at least 1 unused booking credit in their current plan. |
| **Postconditions:** | 1. Booking request has a final status: 'Confirmed' / 'Declined' / 'Rescheduled'.<br>2. A decision record is saved in the Booking_Decisions table with: manager_id, timestamp, decision, reason.<br>3. If Approved: a calendar invite (Google Calendar / Outlook) is sent to both parties; the room slot is blocked in the availability calendar.<br>4. The member's booking credit is decremented by 1 if the decision is 'Confirmed'.<br>5. Push notification + email is sent to the member with the outcome within 2 minutes of the decision. |
| **Priority:** | High — Core feature of the premium workspace plan. Directly affects member retention. |
| **Frequency of Use:** | ~15 booking requests/day per manager. Platform-wide ~300 requests/day across 20 managed locations. Peak on Monday mornings (members planning their week). |
| **Normal Course of Events:** | 1. Facility Manager selects the **Booking Requests** tab in the management portal.<br>2. System displays the pending request queue, sorted by submission time (oldest first), showing: member name, requested room, preferred date/time, and plan tier.<br>3. Manager clicks a request to open the **Request Detail** view.<br>4. System displays full details: member profile, requested room and capacity, preferred slot, and the member's booking history (if any).<br>5. Manager reviews the details and clicks one of three action buttons: **Approve** / **Decline** / **Propose Alternative Slot**.<br>6. System displays a confirmation popup requesting an optional note to the member.<br>7. Manager enters an optional note and clicks **Confirm Decision**.<br>8. System saves the decision to Booking_Decisions, updates the request status, and performs the corresponding action (block slot / release slot / send alternative options).<br>9. System invokes UC-NOTI-02 to send the decision notification to the member.<br>10. System displays a toast "Booking request #[ID] processed" and returns the manager to the queue. |
| **Alternative Courses:** | **UC-ROOM-03.AC.1: Propose an alternative time slot**<br>At step 5 of the Normal Course, if the room is unavailable at the member's preferred time but the manager can offer another slot:<br>5a. Manager clicks **Propose Alternative Slot**.<br>5b. System displays the room's availability calendar for the next 14 days.<br>5c. Manager selects 1-3 alternative slots and clicks **Send Proposal**.<br>5d. System updates the request status to 'Awaiting_Member_Confirmation' and sends the alternative slots to the member.<br>5e. UC ends here for the manager. The member will confirm or decline the alternatives in a separate UC (UC-ROOM-04).<br><br>**UC-ROOM-03.AC.2: Approve with an attached access note**<br>At step 7 of the Normal Course, if the manager wants to share access instructions before the booking:<br>7a. Manager clicks **Attach Note** and uploads a PDF or pastes a URL (max 10MB / 500 chars).<br>7b. System validates the attachment format and size.<br>7c. Manager clicks **Confirm Decision** → continue from step 8 of the Normal Course.<br>7d. The attached note is included in the member's notification email. |
| **Exceptions:** | **UC-ROOM-03.EX.1: Duplicate decision — concurrency conflict**<br>Trigger: At step 8, system detects that the request has already been processed (status changed) since the manager opened the detail view — e.g. a system auto-cancellation or an admin override occurred concurrently.<br>Response: System displays "This booking request was already processed or cancelled. Please refresh the queue."<br>Final state: The manager's current decision attempt is discarded. The request retains its already-updated status. The concurrency event is logged in the audit trail.<br><br>**UC-ROOM-03.EX.2: Slot expired before manager reviews**<br>Trigger: At step 3, the system detects that the member's preferred slot is now in the past (the request sat in the queue too long).<br>Response: System displays a warning banner: "The member's preferred slot has passed. You may still Decline or Propose a new slot — the Approve option is disabled."<br>Final state: Approve button is disabled. Manager can only Decline or Propose Alternative Slot.<br><br>**UC-ROOM-03.EX.3: Calendar Integration Service unavailable**<br>Trigger: At step 8, when the system attempts to create the calendar invite, the Calendar Integration Service times out or returns an error.<br>Response: System saves the decision as 'Confirmed' and displays a warning: "Booking confirmed, but the calendar invite could not be sent automatically. Please share the details manually with the member."<br>Final state: Booking status is 'Confirmed'. Member is notified of approval but without a calendar invite. A retry job attempts to send the calendar invite every 5 minutes for 30 minutes; if it fails, a support ticket is created.<br><br>**UC-ROOM-03.EX.4: Member's booking credit already exhausted**<br>Trigger: At step 8, system checks and finds the member's booking credit = 0 (the credit was consumed by another booking between request submission and approval).<br>Response: System prevents the approval and displays: "This member's booking credit has been exhausted. Approve action is blocked. Please Decline and inform the member to upgrade their plan."<br>Final state: Request is auto-updated to status='Blocked_Credit_Exceeded'. Member receives a notification explaining the situation and a link to upgrade. |
| **Includes:** | UC-NOTI-02: Send booking decision notification (invoked at step 9 of the Normal Course) |
| **Special Requirements:** | **Performance**: Booking request queue loads ≤ 2s with up to 50 pending requests. Request Detail view loads ≤ 1.5s.<br>**Security**: A manager can only view and process requests for their own assigned locations (RBAC). Member personal data displayed in the portal must comply with the platform's privacy policy.<br>**Audit**: Every manager action (view, approve, decline, propose) must be logged with a second-level timestamp. Audit log is retained for 3 years.<br>**SLA**: 80% of booking requests must receive a decision within 24 hours of submission. Requests exceeding 48 hours without a decision trigger an automated escalation to the Operations team. |
| **Assumptions:** | 1. Managers have been onboarded and trained on the management portal.<br>2. Calendar Integration supports both Google Calendar and Microsoft Outlook (OAuth 2.0).<br>3. Booking credit management is real-time — no batch reconciliation. |

Targeted for phase 2. |

## Lessons learned from the two examples

1. **UC-ORDER-01** illustrates a customer-facing checkout UC with payment integration and async fallback handling when the Inventory Service is unavailable.

2. **UC-ROOM-03** illustrates a staff-facing admin UC with concurrency, credit enforcement, and calendar integration edge cases.

3. **Both UCs share**:
   - 1 primary actor + clear secondary actors
   - Description covering WHY + WHAT + OUTCOME
   - Verifiable preconditions (not motivations)
   - Postconditions expressed as system state changes
   - 9-10 step Normal Course alternating Actor/System
   - 2 ACs + 3-4 Exceptions covering key failure modes
   - Special Requirements that are non-functional only
   - Notes with TBDs including owner + due date

4. **Patterns worth learning from these examples**:
   - Async fallback pattern (EX.4 in UC-ORDER-01): payment succeeds but a downstream system fails — never roll back payment, retry asynchronously
   - Quota/credit enforcement at decision time, not request time (EX.4 in UC-ROOM-03)
   - Concurrency conflict handling for multi-actor queues (EX.1 in UC-ROOM-03)
   - Gift card / voucher validation always server-side (security note in Special Requirements)
   - Reference Business Rules by ID rather than inlining them in Normal Course steps
